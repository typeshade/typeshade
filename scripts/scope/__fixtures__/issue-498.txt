# `fill(0)` emits `0.0` elements, and Tint refuses the WGSL

## What happens

`fill<T, N>(v)` builds an `array<T, N>` with every element `v`. It does not type `v` to `T`. A bare `0` is an `f32` on this surface, so `fill<u32, 4>(0)` builds an `array<u32, 4>` of `f32` literals:

```ts
'use typeshade';
export function walk(n: u32): u32 {
  let s: array<u32, 4> = fill<u32, 4>(0);
  s[0] = n;
  return s[0];
}
```

`compile()` reports no diagnostic and emits:

```wgsl
var s: array<u32, 4> = array<u32, 4>(0.0, 0.0, 0.0, 0.0);
```

Tint (Chromium 141.0.7390.37, SwiftShader) refuses it:

```text
error: cannot convert value of type 'abstract-float' to type 'u32'
```

So a program `compile()` accepts does not run. Found while writing proposal 0047 (#495, PR #496).

## Why

`lowerFill` in `src/compiler/ts/lower/expression-array.ts` lowers the value with no expected type and passes it to `fillArray` as it is. `array<T, N>(…)` types each element with `typeArrayElement`, which retargets an integer literal and refuses a value of another type. `fill` skips that step.

## What was expected

`fill<u32, 4>(0)` emits `array<u32, 4>(0u, 0u, 0u, 0u)`, as `array<u32, 4>(0, 0, 0, 0)` does. A value of another type is refused with the element message the list form gives (Rule 12.5), for example `fill<u32, 4>(1.5)`.

## Rules

Rule 1.3 (a program the compiler accepts runs on the target) and Rule 11.3 (the emitted text satisfies Tint).

## Tests owed

- `fill<u32, 4>(0)`, `fill<i32, 3>(-1)` and `fill<vec2, 2>(vec2(1., 2.))` emit typed elements on WGSL and GLSL ES 3.00, and both CPU paths read them.
- `fill<u32, 4>(1.5)` is refused with code and text.
