# User journeys

Programs written the way a TypeScript developer writes them, checked the way a user meets TypeShade.

```bash
bun run build
bun run gate:journeys
```

`scripts/user-journey.ts` packs the tarball the way the publish workflow does (`dist/`, with the manifest rewritten onto it), and installs it into a fresh `npm init` project. It copies the README's `tsconfig.shade.json` into that project verbatim, copies this directory in, and runs `_harness.mjs` there with Node. The harness imports nothing but `typeshade`. For every journey it checks that:

1. `compile()` accepts every `.shade.ts` with no diagnostic, error or warning;
2. the language service (`typeshade/language-service`) reports nothing on it, which is what the editor shows;
3. `tsc -p tsconfig.shade.json` reports only the error classes the README documents: TS1206 on decorators, and operators on vectors;
4. every run produces, on WebGPU (headless Chromium, SwiftShader), what the journey's plain-JavaScript reference computes. The page imports `typeshade/runtime` as the tarball installed it (change 0025), loads the run's manifest (`packModule`), binds each binding by name with the journey's host value, and reads the result back through a `Resident` or the target texture: the harness writes no WebGPU of its own;
5. the same run on the CPU oracle (`compileModule`) produces it too.

The unit suite and the compile gate test the compiler from inside the repository. This gate tests what a user installs and runs. It exists because both kinds of failure it catches had already shipped:

- The README's tsconfig loaded no types at all (#211).
- The first loop a TypeScript author writes, `for (let i = 0; i < data.length; i++)`, did not compile (#209).

## A journey

The import journey also checks private kernel input projection (change 0082): helper reads
across two loops, a reduction, unchanged input objects, invalid unused fields, resident inputs
and a fuse scope. Each result is compared with the same plain-JavaScript reference.

`fieldless-classes/` constructs method-only classes, dispatches an inherited method, and packs
empty class values nested as uniform fields and array elements, checking the GPU result against
the CPU oracle and a JavaScript reference (change 0035).

`workgroup-override/` selects a compute entry's workgroup size from the input length. One source
override names both `@compute`'s dimension and the outer length of its workgroup scratch array;
the WebGPU runtime reports the resolved pipeline shape, the CPU oracle receives the same
selected override and dispatch shape, and the 256-wide run checks the documented WebGL2 refusal
(change 0057).

`workgroup-override-f64/` repeats the specialization through nested workgroup arrays of
emulated doubles. Sizes 32, 64 and 128 run with both fp64 flavors against the CPU oracle and
an independent integer-valued reference. A tail workgroup checks lanes beyond the authored
default extent (#740).

A journey is a directory holding one or more `*.shade.ts` sources and a `journey.mjs` host.

- **The sources** are shader code as their author would write it. Where they spell something a way the author would not, only to get past a gap, the line says so and names the issue. The plasma journey's `const uv: vec2 = …` did, pointing to #162, until the language service learned the type and the annotation came out. A workaround with no issue is not allowed, because the point of the gate is that each one is visible and counted.
- **The host** is plain JavaScript, as the author's own host code would be. It hands each binding a host value (Rule 8.21), as the author would, and the program runtime packs it in the layout WGSL gives it. It also computes, without TypeShade, what the shader should produce. A run with `console` reads the count of lines and of dropped calls from what `submit()` resolves to (change 0028, surface §69), and not from the page's console: a row for each dispatch, or for the draw, of the entry that records, whose lines add up to the ones the sink was handed. `expected` is what one dispatch logs, so a compute run that repeats expects it once for each dispatch, each into a console buffer of its own. The runtime, given a sink, prints no warning for the calls that did not fit, which the harness holds too. A run without `console` resolves to no rows.

A run with `emit` packs its program under those options and runs the manifest as it says (change 0028, surface §69): `journeys/emit-options/` packs a compute entry and a full-screen draw that compute in emulated doubles under the defaults, under each option and under all of them, and holds each result on WebGPU to plain JavaScript's doubles. The `'float'` flavor of the emulation reads the `_fp64` guard and the `'integer'` one reads none, so the bindings follow the flavor, and a manifest that leaves out a guard its WGSL declares is a pipeline WebGPU refuses ("Binding doesn't exist"); a layout may hold a binding its shader never reads, so a guard the manifest lists and its WGSL does not declare is held by `src/core/manifest.test.ts`, not by WebGPU. The harness also fails a run whose manifest does not record the options, and one whose options emit the WGSL the defaults do.

A run with `target` draws into a float target and reads it back as numbers (change 0028, surface §69): `journeys/hdr-target/` draws a fragment entry's values above 1 and below 0 into an `rgba16float` target, each a small dyadic number that is exactly the half float the target stores, and holds what `readFloats()` gives to a plain JavaScript reference within 1e-6, far under one step of a half float's significand. The harness starts the read while the frame is still pending and draws a later frame that clears the target to -1 before the read resolves. It fails the run when the read holds the clear, which is a copy that ran after the later frame, and when the target does not hold the clear afterwards, which is a later frame that did not run.

A run with `depth` draws into a depth target (surface §69): `journeys/depth-stencil/` draws one frame into a `depth24plus` target, a depth-only format, and one into a `depth24plus-stencil8` target, and holds each colour to a reference. The second run checks that WebGPU accepts the pass. A depth attachment with a stencil aspect needs its stencil load and store ops, which the runtime sets to follow the depth: the stencil is cleared to 0 when the depth is cleared, kept when the depth is loaded, and stored. The harness does not read the stencil back. The stencil state of a pipeline is held to pixels in `journeys/pipeline-state/`.

A run with `draws` and `depth32float` or a stencil format draws the pipeline fields of proposal 0064, PR-2: `journeys/pipeline-state/` holds the eight stencil operations against the eight compare functions in each of three places, the stencil masks, the faces, the reference of a pass, the depth bias at three depths and its slope, the WebGL2 bias bound at five depths and the slope threshold, the sample mask, the proposal's decal and stencil outline, and two mixed passes. Each run holds its pixels to a reference computed in plain JavaScript. No run expects a WebGL2 refusal (`webgl2Unsupported`).

A run with `draws` and a depth format of `depth24plus`, `depth24plus-stencil8` or `depth32float`, or a stencil `passes` entry, draws the attachments of proposal 0064, PR-3: `journeys/pass-attachments/` holds the stencil and depth discards against stale write masks, the clears of depth and stencil apart, the read-only depth and stencil with their controls, the translucent pass, and the integer and depth readbacks. Each run holds its pixels, and its depth where it reads one, to a reference computed in plain JavaScript.

A third kind, `kind: 'kernel'`, runs a kernel function (change 0013) and needs no packing: `fn` names it, `args` is its arguments as host values in its parameters' order (`{ particles, sim }`), called `repeat` times; `read` names the argument it writes, which `flatten(value)` turns into floats against `expected`, within `tolerance`. The harness runs it on the CPU oracle; on WebGPU a kernel function runs through the import, so the import path below runs it there. The particles journey is one: its `step` is a loop over `array<Particle>`, with no `@compute`, no `global_invocation_id` and no packing.

A fourth kind, `kind: 'engine'` (change 0025), is a host application rather than a shader run. `engine` names a module of the journey that exports `setup({ device, programs, size })`, which resolves to `{ frame(time), read() }`; `programs` maps each name the engine uses to a `.shade.ts` of the journey, which the harness compiles and hands over as its manifest (`packModule`). The harness refuses the module if it imports anything but `typeshade/runtime` or calls WebGPU itself (a `create…` call, a pass, the queue, `navigator.gpu`, a `GPU…` global or the runtime's `raw` pass). It then gives the module a device, runs `frames` frames at `i / 60` seconds, counts every GPU object the device makes after the first frame (buffers, textures and their views, samplers, bind groups and their layouts, pipelines and shader modules), which must be none, and holds `read()`, the last frame's `size` by `size` RGBA pixels, to `expected()` within `tolerance`. `journeys/engine/` is the gate issue #335 set before a reference engine: two materials that share a camera and lights, a shadow pass, a render to a half-float texture and a tonemap pass, over 60 frames. `journeys/textures/` (change 0028, #404) is a smaller one: a level drawn into an `r32float` texture that the next pass only loads with `textureLoad`, beside two textures that pass samples, one directly and one through a `const` of it, which WebGPU takes only in the layouts the calls that read each texture give.

A fifth kind, `kind: 'fuse'` (change 0058), is a host that calls kernel functions inside `fuse()` from `typeshade/fuse`. `host` names a module of the journey that exports `run(tier, inputs)`: it sets `configure({ prefer: [tier] })`, makes the calls over `Resident` arrays and the scope's scratch arrays (`scope.scratch()`) and resolves to `{ values, report }`. It may import `typeshade/runtime`, `typeshade/fuse` and the `.shade.ts` files of its journey, which the page receives as the Vite plugin generates them, and it may not call WebGPU, as an engine may not. The harness builds the shader modules under `typeshade({ fuse: true })`, the facts a scope fuses by, and runs the host on WebGPU, WebGL2 and the CPU tier. It holds `values` to `expected()` within `tolerance`, and the report's `dispatches` and `submissions` to the run's numbers: on WebGL2 each loop is a draw and there is no submission, and on the CPU tier there is neither. On WebGPU the run gives `webgpu.groups`, the calls of each group in order, and `webgpu.why`, the reason each group after the first gives for standing apart, word for word; a group of more than one call must be reported fused. On WebGL2 and the CPU tier every call is a group of its own: the report of WebGL2 says "WebGL2 runs the calls apart" of each group after the first (a call WebGL2 has no program for falls to the CPU tier there, which says nothing, and the run's `webgl2.why` lists the reasons then), and the report of the CPU tier says nothing. The run's `calls` name every call in order. The harness also holds the report to the device: the page counts `submit` and `dispatchWorkgroups` on their prototypes, and the device must have been given the report's dispatches and its submissions plus the `reads` the host makes. It counts `createBuffer` as well: a run with `arrayBytes` and `webgpu.buffers` is held to the number of buffers of one array's size that the device was asked for, so a scratch array that a fused group holds as a local is a buffer never made, and one that stays a buffer is counted; on WebGL2 and the CPU tier the device is asked for none. `journeys/loop-fuse/` has four runs: `add`, `mul` and `relu` in one scope, with `t` and `u` scratch arrays, one dispatch in one submission on WebGPU and no buffer for either array, the same scope with `pairsum` between `mul` and `relu`, which reads `t[i ^ 1]`, an element another invocation writes, so that the plan makes two dispatches and says why, and the scratch array both dispatches use (`u`) stays a buffer, and `add`, `mul` and `total`, a reduction as the last call of a group (`reduce.mjs`): one loop dispatch that runs the first two calls as the prologue of each iteration of the sum, and one fold dispatch for each level of partials (over 1,000 elements one level, over 70,000 two, a count the journey checks against the length of the arrays), all in the plan's one submission because the levels share a device buffer of partials and the folded slot is copied in that submission, no buffer for `t` or `u`, and the sum held to the plain sum, which for these dyadic inputs is the tree sum, on every tier. `journeys/loop-fuse/bench.mjs` times the chain of the first run four ways on WebGPU, apart, in a scope without the facts, and in a scope with them over `Resident` arrays and over scratch arrays, and `bench-reduce.mjs` times the chain that ends in `total` the same four ways.

A sixth kind, `kind: 'limits'` (change 0051), is a host that runs one program on the runtime's public exports and holds the device's limits to the runtime's words. `host` names a module that exports `refused({ device, program })`, which resolves to the runtime's refusal of the program's entry on the device the page gives (WebGPU's default device, of eight storage buffers per stage), or `null` where it runs, and `requested({ program, size })`, which runs the entry on a device that `createRuntime({ programs })` requests. `program` names the `.shade.ts` the harness packs. The harness runs the second call only where the adapter allows the `need` the entry needs, and reports it as skipped where it does not. `journeys/limits/` holds the first half and the second, with the nine storage buffers of one entry, and its refusal is held to the text of R4 by name.

## The import path

`journeys/_host-import/` is a different kind of journey, and the harness skips it (a name that starts with `_`). It is a Vite project that imports a `.shade.ts` and calls its functions on the CPU tier (surface §64) and its `@compute` entries on WebGPU (surface §67). `scripts/user-journey.ts` sets it up with the documented lines, from the same tarball, beside `vite` and `typescript`, and `tshc sync` runs as its `prepare` script. Beside them npm installs `journeys/_shade-package/`, a shader package the script packs first, which `src/relief.shade.ts` imports by its name (change 0024): the package publishes its shader modules under the `typeshade` condition of its `exports`, so `tshc sync`, the plugin and plain `tsc` read them from the `node_modules` npm laid out. The journeys project installs it too, since the README's `tsconfig.shade.json` covers this directory. It then checks five things:

1. `tsc` over the host program reports 0 errors, and a wrong-length vector argument is TS2345 at the host line;
2. `vite build` bundles it, and the bundle holds no compiler and no `new Function`;
3. Node runs the bundle;
4. every value the bundle prints matches `reference.mjs`, the same computation in plain JavaScript;
5. a browser bundle of `src/gpu.ts` calls two `@compute` entries through the import in a page with WebGPU (change 0016), one of them through a barrier, which has no CPU tier, and both match the reference, called with plain typed arrays and again chained through `resident` arrays, the map's output the block sum's input, which only queue; `markGroups` runs over the workgroup count that `planGroups` wrote into a `resident` array (change 0075), with WebGPU required and again on the CPU tier, each against the reference and the two element for element; and a third, `axpy` of `src/doubles.shade.ts`, over `Float64Array`s its module emulates as two `f32`s each, held to a double's reference within 1e-12; `deep` of `src/deep.shade.ts`, a fragment entry that computes in `f64`, is drawn on WebGPU, WebGL2 and the CPU tier with the `_fp64` guard the runtime binds; it then draws two full-screen fragment entries of `src/draw.shade.ts` on WebGPU, WebGL2 and the CPU tier, each frame against the reference, and a sampled texture's draw on the CPU is refused with the reason, and a third, which reads a `resident` array a kernel function filled, on WebGPU and the CPU tier. It calls the particles journey's kernel function `step` for 20 frames on a `resident` array, whose steps only queue and whose one read follows the last, and draws the plasma journey's `fs` through the import, each against that journey's own reference, and checks that a production build records no `console.*` call while `vite dev` prints an entry's calls from WebGPU in order, each line with its tier, file and line and invocation. It also calls `dstats` of `src/doubles.shade.ts`, a kernel function over 70 000 `f64`s whose map and sum and min run on WebGPU, required, held to a double's reference within 1e-12, and kernel functions of `src/loops.shade.ts` (change 0013), whose loops run on WebGPU one invocation per iteration, each against the f32 reference, two of them reductions whose sums match the tree order bit for bit (300 000 `f32`s, folded over two levels of partials), one a histogram whose bins are atomics, two that read an array's length inside an iteration, over arrays of 5, 12 and 7 elements, the last a `resident` one, whose byte sizes are no multiple of 16 (#367), and renders into and reduces over `resident` arrays that stay on the device across the calls, and one with an array too short for its loop, which is refused before anything is uploaded; and three that use an array's methods on their arrays (change 0079), `methodStats`, `methodFill` and `methodSearch`, whose `reduce`, `fill`, `forEach`, `some` and searches run on WebGPU, required, each against what `Array.prototype` gives.

In the same project, from the same tarball, the script then builds `examples/hosts/` (change 0061) with Vite: the host examples, each a module and the `host.ts` an application would write. It calls each host's `run()` through `examples/hosts/_drive.ts` in two pages. The first has WebGPU and sets `configure({ prefer: ['webgpu'] })`, so a kernel or entry call cannot fall back to another tier. The second hides `navigator.gpu`, sets `configure({ prefer: ['webgl2'] })` and makes each canvas's `webgl2` context first, so every call, draw and `runtime()` runs on WebGL2. Each result is compared with `examples/hosts/_reference.ts`, the reference `examples/host-examples.test.ts` holds the CPU tier to, and a host must pass on a tier exactly when `examples/hosts/_order.ts` lists that tier for it.

`journeys/local-use-inference/` (change 0036, #429) lets direct declared calls establish the
integer type of an unannotated local literal. Its independent JavaScript reference checks
signed division, unsigned wrapping, a shadowed local and a closure on the CPU and WebGPU.

`journeys/local-numeric-contexts/` (change 0037, #429) adds constructor and inherited
constructor arguments, instance and static method arguments, and explicitly typed
initialization and field assignment. Its JavaScript reference checks signed division,
unsigned wrapping and selected object indices against the CPU and WebGPU.

`journeys/function-shadowing/` (change 0039, #429) gives function locals and parameters the
lexical scope inside the module that TypeScript gives them. Its independent JavaScript
