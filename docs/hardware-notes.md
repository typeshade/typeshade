# Hardware notes

This document records what the downstream labs observed on real GPUs. A later backend or runtime
decision can cite an observation here by its id (A1, B3 and so on) and by the lab's record ids.

## What this document is

- **Content.** Each row is an observation made on a physical device through a downstream lab. Today
  the only lab is typecv's SfM lab (`cv.typeshade.dev/lab/`) and its probe page (`/lab/probe/`).
- **Record ids.** A record id is a typecv lab record id, as the lab's collector stores it. A long
  id such as `20261020012028865-b2ca931e` is a run record. A short id such as `14349a11` is a probe
  record, or a run record that the source names by its last eight characters. Record ids are not
  paths in this tree. typecv's
  [lab-run-records.md](https://github.com/typeshade/typecv/blob/cd97b62/docs/lab-run-records.md)
  says how to export them.
- **Chronology.** The labs' own documents hold the chronology and the full numbers. This document
  keeps the facts a compiler decision needs, with a pointer to the source.
- **Labels.** "Observed" is a fact copied from a record. "Inference" is a conclusion from the
  records that no measurement has proven. "Decided" is what an accepted proposal of this repository
  states. "Open" is work that has not run or a question that no record answers.
- **Status.** An observation is not a rule. It becomes a rule only when a proposal in `changes/`
  makes it one and the proposal is accepted (`changes/README.md`). Rule 13.3 requires that a design
  a target might refuse is measured on a device before it is kept. This document is where such a
  measurement can be found again.

### How an observation gets here

An observation comes from one of two sources: a downstream issue on typeshade/typeshade, or the
configuration and validation record of a proposal in `changes/`. To add one:

1. Find the lab's record ids and the lab's commit for the observation.
2. Find the compiler commit that the lab pins at that commit.
3. Add a row to the table of the device, or add a section for a new device.
4. Write the fact, the inference and the open item in separate columns.
5. Name the issue or the proposal that carries the observation.
6. Commit with a `Change: none, <reason>` line, since the document changes no rule.

## What a kernel author should know today

The items below are candidates, not rules. None of them is a design rule of
`docs/language-design.md` yet. Each becomes one only through a proposal in `changes/`, accepted as
`changes/README.md` describes. Until then, an author can read them as advice backed by the records
above.

1. **Clamp idle lanes and mask writes in an entry with heavy loops.** Do not return early for an
   out-of-range lane before the loops. Clamp the lane's index to the last valid item, run the same
   work, and guard each write with an `active` flag. Every lane of a workgroup then runs the same
   control flow. Source: A1. Status: for a kernel function's GPU loop, the compiler's own entries
   take this form since change 0096 (accepted 2026-10-26, implemented in the same session); an
   entry an author writes runs as written (its decision D4), so this advice stands for one. The
   remedy ran on the device on 2026-10-20 and completed where the early return hung (A1).
2. **The first dispatch of a lowered `f64` kernel on D3D12 can take seconds.** That time is the
   shader compile (A2), up to 16 s for a set of kernels on a cold cache. A time budget must not
   count it as work. Today a host excludes it with an untimed dispatch of zero workgroups before
   the first timed chunk (typecv #63). Status: change 0074's open item "Pipeline creation in the
   first chunk".
3. **Do not use the `'integer'` flavor on D3D12.** On the device of A3 its kernels did not finish
   compiling in 57 s. `recommendFp64Flavor` already answers `'float'` there. Status: decided by
   change 0073 for the recommendation. No rule refuses the integer flavor on D3D12.
4. **Do not run a long loop in one dispatch under a watchdog.** Windows resets a device after
   about two seconds, and iOS Safari loses it with no reason (A1, B2). Cut the loop into chunks
   whose state lives in buffers, and run each chunk as a plan of `device.fuse(body, { chunk })`
   (change 0074). typecv's literature review reaches the same design: no source it read delegates
   the cut of a per-thread loop to a compiler (typecv
   [gpu-sfm-research.md](https://github.com/typeshade/typecv/blob/cd97b62/docs/gpu-sfm-research.md),
   "Long kernels under a GPU watchdog"). Status: changes 0074 and 0075 give the runtime half. A
   compiler that cuts loops itself is option C of change 0074, not proposed.
