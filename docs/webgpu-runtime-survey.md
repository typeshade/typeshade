## Part 1. Facts, by question

### A. Device acquisition

**TFJS** (`TFJS/base.ts`)

- Adapter options: `powerPreference` is `'high-performance'`, or `'low-power'` when the flag `WEBGPU_USE_LOW_POWER_GPU` is true (lines 27-31, 33; flag at `flags_webgpu.ts:48`). No `forceFallbackAdapter`.
- Required limits: six, each copied from `adapter.limits` (lines 46-57): `maxComputeWorkgroupStorageSize`, `maxComputeWorkgroupsPerDimension`, `maxStorageBufferBindingSize`, `maxBufferSize`, `maxComputeWorkgroupSizeX`, `maxComputeInvocationsPerWorkgroup`. It requests none of `maxStorageBuffersPerShaderStage`, `maxBindGroups`, `maxComputeWorkgroupSizeY/Z`.
- Required features: `timestamp-query` and `bgra8unorm-storage`, each only when `adapter.features.has(...)` (lines 36-44). No `shader-f16`, no `subgroups`. Line 41 pushes an array (`['bgra8unorm-storage']`), not a string. WebIDL enum conversion stringifies a one-element array to the right name, so the call works by accident.
- Failure handling: there is no `try/catch` and no retry. A failed `requestDevice` rejects the backend factory (lines 59, 26). The factory is registered with priority 3 (line 68). A null adapter would throw at `adapter.features` (line 37).
- Adapter info: `adapter.info`, else `requestAdapterInfo()` (4.22.0, `base.ts:60-66`). `AdapterInfo` keeps `vendor` and `architecture` and derives `intelGPUGeneration` (`adapter_info.ts:18-45`).

**ORT-JS** (`ORT-JS/backend-webgpu.ts`, `wasm/wasm-core-impl.ts`)

- Adapter options: `requestAdapter({powerPreference, forceFallbackAdapter})` with values from `env.webgpu` (`wasm-core-impl.ts:116-124`). The values are validated (`powerPreference` is `'low-power'` or `'high-performance'`, `forceFallbackAdapter` a boolean). When `env.webgpu.adapter` is set, the host's adapter is used and only its shape is checked (lines 131-140). A null adapter throws with a hint about `--enable-unsafe-webgpu` (lines 125-130).
- Required limits: eight, copied from `adapter.limits` (`backend-webgpu.ts:233-241`): `maxComputeWorkgroupStorageSize`, `maxComputeWorkgroupsPerDimension`, `maxStorageBufferBindingSize`, `maxBufferSize`, `maxComputeInvocationsPerWorkgroup`, `maxComputeWorkgroupSizeX/Y/Z`.
- Required features: each only if the adapter has it (lines 247-255): `chromium-experimental-timestamp-query-inside-passes`, else `timestamp-query`; `shader-f16`; `subgroups`.
- Failure handling: no `try/catch` around `requestDevice` (line 257). `onuncapturederror` logs validation errors (lines 280-285). The device is exposed as `env.webgpu.device` (lines 287-292).
- Adapter info: `adapter.info ?? requestAdapterInfo()` (lines 258-268).

**ORT-EP** (native; `ORT-EP/webgpu_context.cc`)

- Adapter options: `backendType` and `powerPreference` from config (lines 78-79). Adapter toggles: `use_dxc`, `allow_unsafe_apis`, `decompose_uniform_buffers`, and on Vulkan `use_vulkan_memory_model` and `vulkan_enable_f16_on_nvidia` (lines 809-817). Device toggles enabled: `skip_validation` (release builds, unless a validation mode is set), `d3d_disable_ieee_strictness`, and `disable_robustness` (lines 827-828, 840, 853). Disabled: `lazy_clear_resource_on_first_use` is toggled at line 855; `timestamp_quantization` is disabled at line 861.
- Required limits (lines 932-956): `maxBindGroups`, `maxComputeWorkgroupStorageSize`, `maxComputeWorkgroupsPerDimension`, `maxStorageBuffersPerShaderStage`, `maxStorageBufferBindingSize`, `maxBufferSize`, `maxComputeInvocationsPerWorkgroup`, `maxComputeWorkgroupSizeX/Y/Z`, all copied from the adapter. One exception: a user option `maxStorageBufferBindingSize` (`webgpu_provider_options.h:59`). A value at or above the 128 MiB guaranteed size is requested from the device. A smaller value is "applied as a logical segmentation limit after device creation" (lines 942-947, 228-231; guaranteed constant at `webgpu_context.h:249-253`). A user option `max_storage_buffers_per_shader_stage` can lower the limit the shader builder sees (lines 232-236).
- Required features, each only if the adapter has it (lines 903-930, list near 906-914): `ChromiumExperimentalTimestampQueryInsidePasses`, `ChromiumExperimentalSubgroupMatrix` (native only), `TimestampQuery`, `ShaderF16`, `Subgroups`, `BufferMapExtendedUsages` (native only).
- Failure handling: `ORT_ENFORCE` on adapter and device status, with Dawn's message (lines 130, 216-219). No retry with fewer features or limits. Device-lost and uncaptured-error callbacks are set (lines 159, 176).

### B. Large tensors

- **TFJS.** No code handles a tensor larger than `maxStorageBufferBindingSize` or `maxBufferSize`. A grep of the whole directory finds the two names only in `base.ts:52-53`. `tensorToBinding` binds the whole buffer (`backend_webgpu.ts:715-731`). `createBuffer` is called with the tensor's byte size and no check (`buffer_manager.ts:44`). So the outcome is WebGPU validation. That outcome is an inference (Part 2, I1).
- **ORT-JS.** Same: no splitting and no size check. A grep finds the two limit names only in `backend-webgpu.ts:236-237`. The bind group entries use `{buffer}` with no offset or size (`program-manager.ts:47-52`).
- **ORT-EP.** It segments. The comment at `webgpu_context.cc:533-539` says that a 200 MB buffer under a 128 MB binding limit is bound as two segments of 128 MB and 72 MB.
  - `CalculateSegmentsForInputsAndOutputs` gives each input and output `ceil(SizeInBytes / maxStorageBufferBindingSize)` segments (`program_manager.cc:69-91`).
  - The bind group layout gets one storage binding per segment (`program_manager.cc:~100-130`). `CreateBindGroup` binds the same `WGPUBuffer` once per segment, with `offset` and `size = min(limit, bufferSize - offset)` (`webgpu_context.cc:1263-1300`, segment math at 1282). A tensor of one segment binds with `WGPU_WHOLE_SIZE` (line 1287).
  - The segment size is the device limit rounded down to `minStorageBufferOffsetAlignment`, so every segment offset is legal (`webgpu_context.cc:237-242`).
  - The shader gets accessor functions `get_<name>_by_offset(global_offset: u32)` and `set_..._by_offset`. They compute `buffer_index = offset / CHUNK_SIZE_IN_ELEMENTS`, `local_offset = offset % CHUNK_SIZE_IN_ELEMENTS`, and `switch` over the segment names `name`, `name1`, `name2`, ... (`shader_variable.cc:321-390`). Shader usage flags are set at `shader_helper.cc:363,369`.
  - Each segment costs a storage binding. `shader_helper.cc:352-354` throws `Too many storage buffers in shader. Current: N, Max is M` against `maxStorageBuffersPerShaderStage`. The layout code throws when the entry count passes `maxBindingsPerBindGroup` (`webgpu_context.cc:1291`).
  - The pipeline cache key includes the segment counts (`webgpu_context.cc:~556`, `CalculateProgramCacheKey(program, inputs_segments, outputs_segments, is_1d_dispatch)`).
- Not found in any of the three: a fallback of a tensor to CPU or WASM because of its size.

### C. Buffer management

**TFJS** (`TFJS/buffer_manager.ts`, `backend_webgpu.ts`)

- Pool key is the exact string `${size}_${usage}` (`buffer_manager.ts:120-122`). No size buckets and no cap on the free list. `acquireBuffer` pops from `freeBuffers` or creates (lines 29-60). `releaseBuffer` pushes back, or destroys when `reuse` is false (lines 62-88).
- Release timing. A tensor whose data id was used in the current command queue is queued in `tensorDataPendingDisposal` and released after the next submit (`backend_webgpu.ts:205-208`, `submitQueue` at 289-309). Uniform buffers wait in `uniformPendingDisposal` and return to the pool after the submit (lines 301-302). Staging buffers wait in `stagingPendingDisposal` and are destroyed (reuse `false`, lines 303-304).
- Upload. Tensor values stay on the CPU until a kernel first needs them (`uploadToGPU`, lines 733-780). The buffer is acquired with `mappedAtCreation = true`. If the pooled buffer comes back unmapped, a `MAP_WRITE | COPY_SRC` staging buffer is made mapped, the values are copied into it, and `copyBufferToBuffer` is recorded into the open command encoder (lines 745-763). The copy is therefore submitted with the dispatches that follow. The host values are dropped after upload (line 775).
- Readback. `getBufferData` acquires a pooled `COPY_DST | MAP_READ` buffer (so the staging buffer is reused by size), records a copy, calls `submitQueue()`, awaits `mapAsync`, copies out with `slice(0)`, unmaps and releases it (lines 338-370). A synchronous `readSync` exists. It copies through an `OffscreenCanvas` and warns that the performance is poor (lines 379-506).
- Small ops stay on the CPU. `shouldExecuteOnCPU` is true when every input is still on the CPU and smaller than `WEBGPU_CPU_HANDOFF_SIZE_THRESHOLD` (default 1000 elements; `flags_webgpu.ts:56`, `backend_webgpu.ts:1036-1043`).
- Memory counters: `numBytesUsed` and `numBytesAllocated` (`buffer_manager.ts:24-25`, `backend_webgpu.ts:216-222`).

**ORT-JS** (`ORT-JS/webgpu/gpu-data-manager.ts`)

- Size buckets: 26 fixed sizes from 64 B to 167,772,160 B, each with a cap on cached buffers (lines 84-113). Examples: `[64, 250]`, `[2048, 230]`, `[1048576, 50]`, `[33554432, 22]`, `[44236800, 2]`, `[167772160, 6]`. A comment at lines 108-109 says that the three largest buckets are cached because "not caching them results in some major performance hits for models like sd-turbo".
- `create(size, usage)` rounds a size up to the first bucket that fits (lines 125-134). A size above the last bucket is rounded up to 16 B, created exactly and never cached (lines 132-134, 328-343, and the `maxInFreeList === undefined` branch at 398-399 destroys it on release). Only buffers with `STORAGE` or `UNIFORM` usage are pooled, in two separate free lists (lines 198-200, 322-339).
- Release timing. `release()` moves the buffer to `buffersPending` (line 371). `refreshPendingBuffers()` runs after `queue.submit` in `flush()` (`backend-webgpu.ts:385-386`) and returns each buffer to its bucket, or destroys it if the bucket is full (`gpu-data-manager.ts:385-430`). In graph-capture mode the buffers are kept for the session instead (lines 417-429).
- Upload. `queue.writeBuffer`. A size that is a multiple of 16 and an offset that is a multiple of 4 take the fast path with no copy (lines 240-243). Otherwise a padded copy is made (lines 244-247). All sizes are normalised to a multiple of 16 B (line 120).
- Readback. `downloadGpuData` creates a new `COPY_DST | MAP_READ` buffer on each call and destroys it in `finally` (lines 149-188). It first ends the compute pass, records the copy and calls `backend.flush()` (lines 161-170), then awaits `mapAsync`.

**ORT-EP** (`ORT-EP/buffer_manager.cc`, `webgpu_context.cc`)

- Six cache modes: `Disabled`, `LazyRelease`, `Simple`, `Bucket`, `Graph`, `GraphSimple` (`buffer_manager.cc:~448-470`). Defaults: storage `Bucket`, uniform `Simple`, query-resolve and default `Disabled` (`webgpu_context.h:136-139`). The bucket table is the same as JSEP's (`buffer_manager.cc:140-165`).
- Upload. If the destination is mapped, `memcpy` into it. Otherwise a `MapWrite | CopySrc` staging buffer is created mapped, copied, and `CopyBufferToBuffer` is recorded, followed by an immediate `Flush` (`buffer_manager.cc:502-535`). A comment (lines 518-522) says that the trailing bytes beyond the real size, up to the 4-byte-aligned copy size, hold uninitialised data.
- Download. Creates a `CopyDst | MapRead` buffer, records the copy, flushes, then blocks in `WaitAny` on `MapAsync` (`buffer_manager.cc:628-672`).
- Initializers use a separate buffer manager with `LazyRelease` caching (`webgpu_context.cc:~265-272`).

### D. Dispatch

**Uniforms.**

- TFJS: each dispatch builds the uniform values (NaN, Infinity, shapes, strides, size, program-defined) into an `ArrayBuffer` with WGSL alignment (`backend_webgpu.ts:782-848`), acquires a pooled `UNIFORM | COPY_DST` buffer of that exact size, calls `queue.writeBuffer(uniformBuffer, 0, ...)` (line 844) and pushes it to `uniformPendingDisposal` (line 845). Bound as `{offset: 0, size, buffer}` (line 847). No dynamic offsets.
- ORT-JS: same pattern. Uniform data is packed with WGSL alignment, including f16 (`backend-webgpu.ts:572-630`). `gpuDataManager.create(size, COPY_DST | UNIFORM)`, `queue.writeBuffer`, then `release()` at once (lines 624-629). The buffer only returns to the free list after the next submit (see C). A comment at line 568 reads `TODO: add cache for uniform (is it necessary?)`. Shapes and strides travel as uniforms, so one shader serves many shapes (see "cache keys").
- ORT-EP: same pattern. The uniform buffer is made in the `Simple` uniform cache, written with `WriteBuffer`, and released to the allocator at once because "the bind group owns a reference now" (`webgpu_context.cc:738, 783-784`).
- None of the three uses `hasDynamicOffset`, a ring buffer, or one shared uniform buffer. (A grep for `hasDynamicOffset|dynamicOffset` finds nothing in the files read.)

**Bind groups.**

- TFJS creates a bind group for every dispatch (`backend_webgpu.ts:948-951`). ORT-JS does too (`program-manager.ts:56-60`). ORT-EP does too (`webgpu_context.cc:778`, `CreateBindGroup` at 1263-1303).
- The only reuse is graph capture and replay. ORT-JS stores `{computePipeline, bindGroup, dispatchGroup}` in `capturedCommandList` while `sessionStatus === 'capturing'` (`program-manager.ts:62-71`) and `replay()` re-issues them (`backend-webgpu.ts:894-923`). Capture needs stable buffers: re-registering a different external buffer under capture throws (`gpu-data-manager.ts:292-295`), and intermediate buffers are not recycled in capture mode (lines 417-429). ORT-EP has the same capture state (`CapturedCommandInfo`, `webgpu_context.cc:~340-360` and `CaptureBegin/Replay`). `enableGraphCapture` requires outputs at the `gpu-buffer` location (`wasm-core-impl.ts:454-472`).

**Pipeline and shader cache keys.**

- TFJS: `makeShaderKey` = program key + workgroup size + ranks of the shapes + dtypes + variable names + broadcast dims + "input shape equals output shape" flags + `flatDispatch` (`webgpu_program.ts:350-381`). Shapes themselves are not in the key (they travel as uniforms), only ranks. The matmul program adds the "fits" booleans (`fitAOuter`, `fitBOuter`, `fitInner`), `isVec4`, `isVectorA`, elements per thread, transposes and the activation (`matmul_packed_webgpu.ts:551-554`). `pipelineCache` is a plain object, unbounded (`backend_webgpu.ts:119, 889-893`). `layout: 'auto'` (`webgpu_program.ts:85-93`). Pipelines can be built with `createComputePipelineAsync` when `WEBGPU_ENGINE_COMPILE_ONLY` is true (lines 83-88).
- ORT-JS: key = `name[hint]:is1DimensionDispatch:<input info>` (`backend-webgpu.ts:95-115`). Each input contributes its `dims` or only its `rank`, as the program's `shaderCache.inputDependencies` says (default `'dims'`). The matmul uses `['rank','rank']` and a hint of `elementsPerThread;activation;isVec4;isChannelsLast` (`matmul_packed_webgpu.ts:487, 540`). `layout: 'auto'` (`program-manager.ts:115-119`). The repo is an unbounded `Map` (line 22).
- ORT-EP: key includes the program name, hint, input dependencies, segment counts and `is_1d_dispatch` (`webgpu_context.cc:~556`). Pipelines build asynchronously and a window of deferred dispatches waits for them before encoding (`webgpu_context.cc:~360-470`).

**Command encoder batching.**

- TFJS: one command encoder; a compute pass stays open across dispatches; the batch is submitted after `WEBGPU_DEFERRED_SUBMIT_BATCH_SIZE` dispatches, default 15 (`flags_webgpu.ts:23`; test at `backend_webgpu.ts:983-986`). A dispatch inside `time()` ends the pass and gets its own query (lines 983-991). A read, a copy or a draw also submits.
- ORT-JS: `maxDispatchNumber = 16` (`backend-webgpu.ts:200`). After each dispatch, `pendingDispatchNumber++`; at 16, or after each dispatch when timing with `at-passes`, the pass ends, and at 16 `flush()` finishes the encoder and submits (`program-manager.ts:77-87`, `backend-webgpu.ts:351-388`).
- ORT-EP: `max_num_pending_dispatches_ = 16` (`webgpu_context.h:472`, option `ep.webgpuexecutionprovider.maxNumPendingDispatches`, `webgpu_provider_options.h:64`). The comment at `webgpu_context.cc:798-799` says a full window is drained and submitted "to bound both recorded and encoded dispatch state". Deferral is only for pipeline compilation: dispatches record in a window, the window waits for all pipeline builds, then it encodes (lines ~360-470).

**Dispatch size limits.**

- All three fold the same way. If any of x, y, z exceeds `maxComputeWorkgroupsPerDimension` (read from the device, not the adapter): try `ceil(sqrt(total))` as `[n, n, 1]`; if that still exceeds the limit, `ceil(cbrt(total))` as `[n, n, n]`; else throw `Total dispatch size exceeds WebGPU maximum`.
  - TFJS: `reshapeDispatch` (`backend_webgpu.ts:71-97`). It asserts that the program has no `y` or `z` layout (lines 82-85).
  - ORT-JS: `normalizeDispatchGroupSize` (`program-manager.ts:125-146`). It uses `x*y*z` as the total.
  - ORT-EP: `NormalizeDispatchGroupSize` (`program_manager.cc:50-67`). It skips this for an indirect dispatch (`webgpu_context.cc:~547-554`).
- The shader rebuilds a linear index from the folded dispatch:
  - TFJS: `(workgroupId.z * numWorkgroups.x * numWorkgroups.y + workgroupId.y * numWorkgroups.x + workgroupId.x) * flatWorkgroupSize + localIndex` (`webgpu_program.ts:215-224`). A flat 1D dispatch keeps `globalId.x`.
  - ORT-JS: `workgroup_index * (wgX*wgY*wgZ) + local_idx` (`ops/common.ts:881-897`), a different shader text for 1D, so `is1DimensionDispatch` is part of the cache key. Elementwise programs also end with `if (global_idx >= size) { return; }` (`common.ts:848-852`).

### E. Profiling

- TFJS: timing runs only inside `backend.time(f)`. When the device has `timestamp-query` (`backend_webgpu.ts:147`), each dispatch gets a compute pass with `timestampWrites` (4.22.0: object form with `beginningOfPassWriteIndex: 0`, `endOfPassWriteIndex: 1`, lines 957-969; 4.9.0 used an obsolete array form) on a query set of 2 entries, reused (lines 124, 959-963). Then `getQueryTime()` runs: `resolveQuerySet` into a `QUERY_RESOLVE` buffer, copy to a pooled `MAP_READ` buffer, `submitQueue()`, `await mapAsync`, `(end - start) / 1e6` as milliseconds (lines 997-1027). So each timed kernel is its own submission and its own await. Results are `{name: program.constructor.name, query: Promise<number>}`, summed into `kernelMs` (lines 649-702). Without the feature it returns 0 and warns once (lines 650-658, 1005-1007).
- ORT-JS: query type is `inside-passes` when the device has `chromium-experimental-timestamp-query-inside-passes`, else `at-passes` when it has `timestamp-query`, else `none`. It is set only when profiling mode is `default` or tracing is on (`backend-webgpu.ts:851-874`). The query set holds `maxDispatchNumber * 2` entries (32) with one resolve buffer (lines 863-871). Each dispatch gets two indices, `pendingDispatchNumber * 2` and `+ 1` (`program-manager.ts:45, 76`). `at-passes` makes one pass per dispatch with `timestampWrites` indices (backend-webgpu.ts:331-337, and `program-manager.ts:79-84`). `inside-passes` calls `writeTimestamp` inside one pass (lines 843-850).
  - At `flush()` it resolves all query pairs of the batch, creates a `MAP_READ` buffer, and copies in the same encoder before `submit` (lines 360-383). It then calls `mapAsync` without awaiting and fills in the result later through a callback (lines 390-457). A map `pendingQueries` ties each read buffer to its list of `PendingKernelInfo` (lines 206, 374, 393).
  - Reporting: for each dispatch, `startTime` and `endTime` are nanoseconds relative to the first timestamp ever read (`queryTimeBase`, lines 406-415). They are given with kernel id, kernel type, name, program name and input and output dims and types to `env.webgpu.profiling.ondata` (version 1), or printed with `console.log` (lines 417-450).
- ORT-EP: the same design. `WriteTimestamp` only when the type is `InsidePasses` (`webgpu_context.cc:958-964`). A query set of `max_num_pending_dispatches_ * 2` (line 980). At flush: `ResolveQuerySet`, a read buffer per flush, `pending_queries_` (lines ~1236-1255). GPU timestamps are shifted onto the CPU timeline of the ORT profiler with an offset taken at the first submit (`CollectProfilingData`). The device toggle `timestamp_quantization` is disabled (line 861), which removes Chrome's coarse rounding.

### F. f16

- TFJS 4.22.0: no f16 anywhere. A grep for `f16|float16|shader-f16` in `TFJS/` (non-test files) finds nothing. `GPUBytesPerElement` supports only float32, int32, bool, string and complex64 (`webgpu_util.ts:146-155`). Every storage array is `f32`, `i32` (the upload code copies through `Float32Array` or `Int32Array`, `backend_webgpu.ts:752-756`).
- ORT-JS: requests `shader-f16` when the adapter has it (`backend-webgpu.ts:253`). At shader build, `enable f16;` is prepended when `device.features.has('shader-f16')` (and `enable subgroups;` likewise) (`program-manager.ts:96-111`). The shader type for a float16 tensor is `f16` or `vecN<f16>` (`ops/common.ts:223-224`). Uniforms of type float16 are written as `Uint16Array` with their own alignment rules (`backend-webgpu.ts:581-598, 615-616`). A tensor is a byte buffer, so f16 data uploads as raw 16-bit values.
- ORT-EP: same request (`webgpu_context.cc:912`). A program whose input or output is `FLOAT16` writes `enable f16;`, and returns the error `Program <name> requires f16 but the device does not support it.` when the device lacks the feature (`shader_helper.cc:~465-472`; the check is at line 471). A grep for `pack2x16float`/`unpack2x16float` in `ORT-EP` and `ORT-JS` finds one file, `tensor/scatter_elements.cc`, which is not an f16 fallback. So neither ORT path has a software f16 fallback in the files read. Adapter toggles `use_dxc` and `vulkan_enable_f16_on_nvidia` (lines 812, 817) exist so that f16 is exposed on D3D12 and on NVIDIA Vulkan.
- Packed sub-word storage exists elsewhere in ORT-EP, for a different purpose: `bool` vectors are stored in `u32` and unpacked by mask (`shader_variable.cc:~323`), and the 64-bit types are stored as `vec2<u32>` (lines ~320-321). The 4-bit `MatMulNBits` operators read packed words (`ORT-JS/webgpu/ops/matmulnbits.ts`).

### G. Workgroup size and tiling

- Elementwise and generic programs: ORT-JS uses `WORKGROUP_SIZE = 64` (`ops/common.ts:18`). The native matmul-adjacent elementwise code also uses 64 (`ORT-EP/math/matmul.cc:~177`, `CeilDiv(output_size, 64u)`).
- Matmul, ORT-JS: workgroup `[8, 8, 1]`; elements per thread `[4, 4, 1]`, or `[4, 1, 1]` when `dimAOuter <= 8`; `isVec4 = dimInner % 4 === 0 && dimBOuter % 4 === 0`; the dispatch is `[ceil(N/8/4), ceil(M/8/epts_y), ceil(batch/8/1)]` (`matmul_packed_webgpu.ts:463-472`). A 32x32 output tile, with shared arrays `mm_Asub` and `mm_Bsub` of `tileInner` rows (lines 118-119, 348-349). The code throws if the tile sizes are not divisible by the workgroup (lines 105-115, 223-227).
- Matmul, ORT-EP: `MATMUL_PACKED_WORKGROUP_SIZE_X/Y/Z = 8, 8, 1` (`math/matmul.h:70-72`), the same `[4,4,1]` or `[4,1,1]` rule (`math/matmul.cc:310-312`), and a separate `MatMulGemvProgram` for the vector case (`matmul.cc:49-63, 300-306`).
- Matmul, TFJS: `computeWorkgroupInfoForMatMul` returns workgroup `[8, 8, 1]`, elements per thread `[4, 4, 1]`; `elementsPerThread[1] = 1` when `dimAOuter <= 8`; `workgroupSize[0] = 4` when `dimInner <= 16 && dimBOuter <= 16` (`webgpu_util.ts:67-91`). The comment at lines 70-76 gives the reason for the small workgroup: "WebGPU limits the maximum allowed shared memory size as 16K". The vector-times-matrix program uses `[32, 1, 1]` (`matmul_packed_webgpu.ts:518-521`). The vec4 path requires `dimInner % 4`, `outputShape[2] % 4` and `!transposeB` (lines 512-514). Shared B tile is `array<array<vec4<f32>, tileBOuter/4>, tileInner>` (line 167).
- Matmul variants chosen by occupancy, TFJS: if the 32x32-tile workgroup count is at most `thresholdToIncreaseWorkgroups` (8, or 16 on Intel gen 12 and later), pick `MatMulReduceProgram` (output at most 128 elements), `MatMulSplitKProgram` (batch 1 and inner at least 2000), or `MatMulSmallOutputSizeProgram`; else the packed program (`kernels/BatchMatMul_impl.ts:104-137`; threshold set at `backend_webgpu.ts:148-149`; Intel generation from `adapter_info.ts:31-40`).
- Conv, TFJS: workgroup `[16,16,1]`, `[4,16,1]` or `[16,4,1]` by output shape; vec4 variant `[8,8,1]` with `[4,4,1]` work per thread (`webgpu_util.ts:93-140`).
- Dependence on limits and on the adapter:
  - Limits: ORT-JS checks the requested workgroup against `maxComputeWorkgroupSizeX/Y/Z` and `maxComputeInvocationsPerWorkgroup` when it builds the shader, and throws with the numbers (`ops/common.ts:859-879`). TFJS makes no such check. Neither ORT nor TFJS picks a tile from `maxComputeWorkgroupStorageSize`; both request the adapter's value (`base.ts:48`, `backend-webgpu.ts:234`) and choose tiles that fit the 16 KiB default.
  - Adapter: TFJS uses vendor and architecture for one threshold (above). ORT-JS disables the vectorised grouped convolution on `ampere` (`ops/conv.ts:195-199`) and uses a path for Intel `gen-12lp` in `matmulnbits.ts:491-492`. ORT-EP has `SplitKConfig`, a table of split-K thresholds per Intel architecture: disabled for `gen-7/8/9/11`, three threshold sets for `xe-2lpg/2hpg/gen-12hp`, `xe-3lpg` and the rest, and nothing for other vendors (`ORT-EP/webgpu_utils.cc:28-76`). It also enables `subgroup_matrix` paths by feature, not by vendor.
  - So: tile and workgroup shapes depend on tensor shapes. Occupancy and split-K heuristics, and correctness workarounds, depend on vendor and architecture.

### H. Other points relevant to a training loop

- Keep data on the GPU. TFJS: `createTensorFromGPUData` wraps a user `GPUBuffer` (with or without a copy, `zeroCopy`) and `readToGPU` returns a new buffer (`backend_webgpu.ts:556-630`). ORT-JS: `registerBuffer` for external buffers with ids (lines 801-817), `preferredOutputLocation: 'gpu-buffer'`, and graph capture (`wasm-core-impl.ts:418, 454, 470`).
- Avoid readbacks. TFJS warns on `readSync` (`backend_webgpu.ts:399-404`) and keeps small CPU tensors on the CPU (above). ORT's download first flushes the open encoder so the read sees the queued work (`gpu-data-manager.ts:161-170`).
- Error scopes. ORT-JS wraps each kernel in `pushErrorScope('validation')` when `env.debug` is on, and collects the popped errors per kernel (`backend-webgpu.ts:768-790`).
- ORT-EP drops validation (`skip_validation`) and robustness in release builds, for speed (above).

## Part 2. Inferences (labelled)

- I1. [Inference] A tensor above the binding limit in TFJS or in ORT-JS fails in WebGPU validation at `createBindGroup` or at dispatch. The sources contain no check. WebGPU validation rejects a binding larger than `maxStorageBufferBindingSize`. The spec text was not re-read for this report.
- I2. [Inference] Requesting every adapter limit (all three runtimes) makes the device's limits equal to the adapter's. Therefore code that reads `device.limits` at use time sees real values, and no run needs a refusal at request time. The cost is that a program's real need is never recorded, and a run on a larger adapter can pass where a smaller one fails, with no message that names the limit. The sources do not measure any performance effect of a larger limit.
- I3. [Inference] ORT's choice of a bind-group-per-dispatch plus capture/replay means ORT treats bind-group creation as cheap relative to the risk of a stale buffer. The only reuse is in a mode where buffers are held fixed. This matches the constraint in the TypeShade WIP, where only "kept" buffers (a Resident's buffer and the uniform ring) may appear in a cached bind group.
- I4. [Inference] The batch sizes 15 (TFJS) and 16 (ORT) are empirical. The only stated reason is ORT-EP's: "bound both recorded and encoded dispatch state" (`webgpu_context.cc:798`). No source gives a measurement.
- I5. [Inference] The 16 KiB default of `maxComputeWorkgroupStorageSize` is the real tile budget in both libraries. TFJS says so in a comment (`webgpu_util.ts:70-76`). A 32x32 f32 A tile plus a 32x32 f32 B tile is 8 KiB.
- I6. [Inference] Neither ORT nor TFJS has an f16 fallback for a device without `shader-f16` in the files read. ORT's behaviour for an fp16 model on such a device (error at shader build, or an earlier fallback to the CPU provider at graph partitioning) was not traced: only the shader-build error was read.
- I7. [Inference] Chrome's timestamp rounding and the need for `allow_unsafe_apis` are why ORT-EP disables `timestamp_quantization` and why TFJS prints a flag hint (`backend_webgpu.ts:650-658`). The TFJS text names a Dawn flag; the ORT-EP code names a toggle. The Chrome behaviour itself was not re-read.

## Part 3. Recommendations (all are Proposals unless they say otherwise)

Convention: **Copy** is what to adopt, **Avoid** is what to leave, each with its reason.

### 3.1 TypeShade proposal 0051 (accepted): request, report, refuse

State of our baseline (fact, from `origin/main` at `96dbaa9f` as proposal 0051 records it): `createRuntime()` calls `adapter.requestDevice({requiredFeatures})` with no limits (`src/runtime/runtime.ts:478-489`). The call layer calls `requestDevice()` with no descriptor (`src/core/host-entry.ts:668-670`). Both devices therefore run on WebGPU's default limits.

- **Copy: report the device's limits, not the adapter's.** All three runtimes read `device.limits` at use time for dispatch folding and workgroup checks (`TFJS/backend_webgpu.ts:75`, `ORT-JS/program-manager.ts:131`, `ORT-JS/program-manager.ts:109`). 0051's `rt.limits` and `callDevice()` do the same and add the host-visible record.
- **Copy: a refusal that names numbers.** ORT's two build-time refusals are the model: `Too many storage buffers in shader. Current: N, Max is M` (`shader_helper.cc:352-354`) and `workgroup size [x,y,z] exceeds the maximum workgroup size [..]` (`common.ts:864-878`). 0051's R4 text (entry, line, limit, both numbers) carries more context than either. Keep it.
- **Copy: a segmentation limit that is lower than the device's.** ORT-EP lets the host name a smaller `maxStorageBufferBindingSize` and applies it "as a logical segmentation limit after device creation" (`webgpu_context.cc:228-231, 942-947`). A test and a user can then exercise the sharding path on a large device. 0051's `limits` request cannot lower a device limit (WebGPU only raises). Proposal: TypeNN should accept its own `shardBytes` override (it already does in `src/data/shards.ts`) and the runtime need not change.
- **Copy: round the usable binding size down to `minStorageBufferOffsetAlignment`** wherever a binding is cut at an offset (`webgpu_context.cc:237-242`). Add it to `rt.limits` documentation if offset windows are ever used (see 3.5).
- **Avoid: requesting every adapter limit, as all three do.** 0051 derives the need from the manifest, adds the host's named limits and keeps the request minimal. That makes the pipeline refusal (R4) meaningful and the failure reproducible on another adapter. The references cannot offer either (I2). Keep 0051's design.
- **Gap that neither reference fills, and 0051 leaves open:** `maxComputeWorkgroupStorageSize`. 0051 does not derive it because the manifest has no workgroup memory size (0051, "The limits the runtime does not derive"). Both references request the adapter's value and still stay inside 16 KiB (I5). Proposal for the 0069 work: record the workgroup memory size of an entry in the manifest in a later schema revision, so that R4 can refuse a tile over the device's value. Until then, design tiled entries to fit 16384 B.
- **Optional, low priority:** a one-line host switch such as `limits: 'adapter'` that requests everything, as ORT and TFJS do, for a host that wants their behaviour. Not recommended as a default (see Avoid).

### 3.2 TypeShade C9/C10 runtime work (PR #658): bind group cache and dynamic-offset uniform ring

Fact about the WIP (`fa347ad7`, "not verified" by its own message): a per-device `WeakMap` holds one uniform `ring` buffer (starting at 4096 B, doubling), and a bind-group `Map` capped at 512 and cleared when full. Uniforms are written at offsets that are multiples of `minUniformBufferOffsetAlignment` (default 256) and bound with `hasDynamicOffset: true`. Only buffers registered by `keepBuffer` (a Resident's buffer and the ring) enter a cached bind group. `forgetBuffer` drops the groups of a buffer before it is destroyed or replaced.

- **Keep (no reference does it): the ring with dynamic offsets.** Fact: the three references write one pooled uniform buffer per dispatch (3.2 Facts, D). A ring replaces N allocations and N pool operations per flush with one buffer and N `writeBuffer` calls. Inference: this is correct under the queue timeline, as the WIP's comment states, because `writeBuffer` executes in order with `submit`. The reference code gives no evidence either way.
- **Copy: the invariant "a cached bind group names only buffers that stay".** ORT's capture/replay keeps the same invariant by forbidding a changed external buffer and by not recycling buffers while capturing (`gpu-data-manager.ts:292-295, 417-429`). The WIP's `kept` set plus `forgetBuffer` is the same rule, applied per buffer. Add a test for the dangerous path: a Resident replaced by a write that changes its length (the WIP handles it in `resident.ts`), and a ring growth while cached groups exist.
- **Check before merge (inference-level risks, none is shown by the references):**
  1. The size of a dynamic-offset uniform binding (`size: u.size`) must be at least the shader struct's minimum binding size. ORT and TFJS round the uniform buffer up to 16 B (`backend-webgpu.ts:603-606`, `backend_webgpu.ts:828-829`). Confirm that the WIP's `packed()` result is rounded to the struct size.
  2. `minUniformBufferOffsetAlignment` is 256 by default. The WIP reads `d.limits?.minUniformBufferOffsetAlignment ?? 256`. This is right. Note that 256 B per uniform per dispatch is much larger than ORT's 16 B packing. A 1,000-dispatch scope uses 256 KB.
  3. The bind group cache key contains the pipeline id, group, binding, buffer id, offset and size, and not the dynamic offsets. This is correct, since offsets are passed at `setBindGroup`.
  4. `MAX_GROUPS = 512` with a clear-all policy: both references keep pipeline caches unbounded and have no bind-group cache to compare with. A training loop reuses the same few groups every step, so 512 is probably enough. Add a counter to the benchmark (`scripts/bench-fuse-scope.ts`) that reports cache hits and clears, to confirm.
- **Avoid: copying the 15 or 16 dispatch cap.** The caps bound ORT-EP's recorded state and pipeline waits (I4). TypeShade's `DispatchBatch` records one plan into one encoder and submits once (proposal 0066, item 3). A cap adds submissions with no measured benefit. If a cap is needed to bound memory, bound the ring (for example, flush at 1 MiB of uniforms).
- **Copy: release resources only after the submit that uses them.** All three do (TFJS `submitQueue`, JSEP `refreshPendingBuffers`, native `RefreshPendingBuffers` after `Submit`). The WIP's ring destroys the old buffer in `ringFor` immediately on growth. WebGPU defers the real free of a destroyed buffer until the queue finishes its work, so this is safe in the spec's model, but the cached bind groups are dropped first, which is the part that matters.

### 3.3 TypeShade 0066: GPU time per fuse group

- **Copy: batch the queries per submission and read them without blocking.** ORT-JS and ORT-EP size one query set for the whole batch (2 entries per timed pass), resolve once into one buffer, copy to a `MAP_READ` buffer in the same encoder, and `mapAsync` without awaiting (`backend-webgpu.ts:360-390`; `webgpu_context.cc:~1236-1255`). This matches 0066 items 3 and 4, and the plan's `submissions` count does not change.
- **Avoid: TFJS's per-kernel submit and await** (`backend_webgpu.ts:983-991, 997-1027`). It changes the schedule it measures and defeats batching.
- **Copy: the object form of `timestampWrites`** (`beginningOfPassWriteIndex`, `endOfPassWriteIndex`). TFJS 4.9.0 used an old array form that was replaced in 4.22.0 (`backend_webgpu.ts:965-969`). Write the descriptor to the current spec, and add a WebGPU test that fails if the browser rejects it.
- **Avoid: `chromium-experimental-timestamp-query-inside-passes` and `writeTimestamp` inside a pass** (`backend-webgpu.ts:249-252, 843-850`). It needs an unsafe-API flag and only ORT's profiler uses it. 0066 uses the standard feature, with one pass per group, which is the `at-passes` path in ORT.
- **Copy: report times relative to a base, in integer nanoseconds, and check `Number.isSafeInteger`** (`backend-webgpu.ts:406-415`). 0066 says "nanoseconds"; a `BigUint64Array` difference converts safely only for a bounded range.
- **Add to 0066's implementation notes:** a group's query pairs share one query set, so size the set by the number of passes of the plan (a reduction group has several). The set is limited by the spec (4096 queries is the spec maximum; this number is from the WebGPU spec, not from the sources, so confirm it). The group that overflows reports no `gpuTime`, which 0066 item 5 already allows.
- **Warn in docs:** rounding of timestamps (I7). ORT-EP disables the Dawn toggle (`webgpu_context.cc:861`). A browser host cannot. 0066's "no test assumes a step" is the correct stance.

### 3.4 TypeShade 0067: kernel workgroup size, and 0069: tiled entry in a fuse scope

- **0067, copy: workgroup size as a compile-time property of the kernel, in the pipeline key.** TFJS puts the workgroup size in its shader key (`webgpu_program.ts:375`), ORT bakes the size into the WGSL text and into the cache hint for tile shapes (`matmul_packed_webgpu.ts:540`). `@workgroup_size([TILE])` plus F7 matches this. Reference defaults for reasoning about a benchmark: 64 for elementwise (ORT-JS), `[8,8,1]` with `[4,4,1]` per thread for matmul in all three, `[16,16,1]` or `[8,8,1]` for conv in TFJS.
- **0067, copy: a build-time check against the device's limits that prints the shape and the limit.** ORT's check is `ops/common.ts:859-879`. 0051's `checkWorkgroupShape` is the same check, and 0067's TS8026 warning covers the compile-time side with WebGPU's default limits. Make sure the runtime check reads `rt.limits`, as 0051 says.
- **0067, avoid: per-vendor workgroup sizes.** Fact: no reference picks a workgroup size by vendor. They vary tile shape by tensor shape, and use vendor or architecture only for split-K or occupancy thresholds and for correctness workarounds (`adapter_info.ts`, `webgpu_utils.cc:28-76`, `conv.ts:199`). A fixed attribute per kernel, as 0067 declares, is the same level of tuning.
- **0067 acceptance:** the proposal says the profile numbers are owed. The references show the shapes to measure: elementwise at 64 and 256, matmul at `[8,8]`, small-M matmul with `elementsPerThread[1] = 1` (dimAOuter at most 8).
- **0069, copy: the matmul tiling as the first tiled entry.** Workgroup `[8,8,1]`, 4x4 outputs per thread, a 32x32 output tile, `tileInner` 32, a vec4 path when `dimInner % 4 == 0` and `dimBOuter % 4 == 0`, workgroup memory 8 KiB for f32 (`matmul_packed_webgpu.ts:144-170, 463-474`; `webgpu_util.ts:67-91`). Fits the 16 KiB default.
- **0069, copy: specialise on divisibility.** TFJS builds the "fits" booleans into the shader key and so removes bounds checks (`matmul_packed_webgpu.ts:551-554`). ORT passes the dimensions as uniforms and keys on rank only, so one shader serves many shapes (`matmul_packed_webgpu.ts:487`). For a training loop, where shapes repeat every step, TFJS's specialisation gives faster shaders. ORT's gives fewer pipelines. TypeShade's pipeline cache is keyed by entry, so the author's choice of `override` constants versus uniforms decides this. Propose the TFJS style for fixed-batch training.
- **0069, note a gap that the references fill and 0069 does not:** both references fuse the bias and the activation into the matmul's epilogue (`matmul_packed_webgpu.ts:503-508, 546-548`, `activationFnSnippet`; ORT `matmul.ts` `activation` attribute). 0069 gives the entry its own group and does not contract the following map (its "Trade-off" says so). For TypeNN training, that costs a dispatch and a round trip through memory for each bias add. A later proposal could give a tiled entry an epilogue hook. This is outside 0069 and is flagged as open work.
- **0069, copy: low-occupancy variants.** TFJS switches to reduce, split-K or small-tile programs when the 32x32 tile count is at most 8 (16 on Intel gen 12 and later) (`BatchMatMul_impl.ts:104-137`). Backward passes with a small batch hit this case. Measure before adding it.
- **0069, determinism note.** The split-K and reduce variants change the sum order. 0069's Q2 on sum order and bit equality with the CPU oracle applies: do not copy split-K into an entry that has a bit-equality claim.

### 3.5 A future f16 proposal: storage f16 with a software fallback when `shader-f16` is absent

- **Copy: detect by the adapter, request optionally, emit `enable f16;` only when the device has the feature** (`backend-webgpu.ts:253`, `program-manager.ts:96-111`). Report the enabled feature in `callDevice().features` (0051 already lists it).
- **Copy: handle f16 uniforms specially.** ORT writes f16 uniforms as `Uint16Array` with their own alignment (`backend-webgpu.ts:581-598`). If TypeShade ever puts f16 in a uniform, use the same layout.
- **Avoid: ORT's behaviour on a missing feature** (an error at shader build, `shader_helper.cc:471`). The proposal asked for a software fallback. No reference has one (Part 1, F), so the design is new work.
- **Proposal for the fallback design (not in the sources):** store the data as `array<u32>`, two halves per word, on every device (the device-resident dataset already stores u8 four per word). On a device with `shader-f16`, a kernel may reinterpret the same buffer as `array<f16>` through a second pipeline variant that is keyed by the feature. Without it, a kernel loads with `unpack2x16float` and stores with `pack2x16float`, both core WGSL, and accumulates in f32. This keeps the buffer layout identical on both paths, so a Resident can move between devices.
- **Risk to settle in that proposal (inference):** the rounding of `pack2x16float` is implementation-defined for values outside the f16 range, and its tie-breaking is not stated in the sources. So the software path and the `shader-f16` path may differ in the low bit. A bit-equality claim against the CPU oracle must define the oracle's rounding, or the proposal must limit the claim to a tolerance. Read the WGSL spec text for `pack2x16float` before writing the rule. This was not done for this report.
- **Copy: the "report the reason" habit.** ORT's error names the program and the missing feature. A TypeShade refusal of an f16 program on a device without the feature should be a `TypeError` that names the entry, as 0051's R4 does for limits.

### 3.6 TypeNN device-resident datasets (PR #20): sharding and which limit to plan against

Numbers for CIFAR-10 train (computed here): 50,000 samples of 3,072 bytes each is 153,600,000 B. The default `maxStorageBufferBindingSize` is 134,217,728 B (128 MiB), so `floor(134217728 / 3072) = 43,690` samples fit in one shard (134,215,680 B) and the rest, 6,310 samples (19,384,320 B), fit in a second. The default `maxBufferSize` is 268,435,456 B, so the whole source also fits in one buffer. The 256-byte offset alignment divides 134,215,680 (it is 524,280 times 256) and 3,072, so a single buffer could also be bound in two windows. (The default limits and the 128 MiB guarantee are WebGPU facts that ORT also states at `webgpu_context.h:249-253`.)

**Which limit to plan against when the runtime does not expose the device's real limits.**

- **Plan against WebGPU's guaranteed defaults.** That is what our devices have today (baseline `runtime.ts:478-489`, `host-entry.ts:668-670`), and what ORT-EP's code treats as the floor (`webgpu_context.h:249-253`). Use 134,217,728 B for a binding, 268,435,456 B for a buffer, and 8 storage buffers per stage. This is the current `DEFAULT_SHARD_BYTES` in `src/data/shards.ts:6`; keep it.
- **When 0051 lands, read the device's real values and prefer them.** Use `rt.limits.maxStorageBufferBindingSize` and `rt.limits.maxBufferSize`, or `callDevice().limits` for the call layer. If the dataset does not fit in one binding, a host may raise the limit with `createRuntime({ limits })` or `configure({ limits })` before the device exists, and TypeNN may accept a `shardBytes` of 0 meaning "use the device's limit".
- **Do not request every adapter limit to avoid sharding** (the ORT/TFJS habit). The limit is not guaranteed across adapters, and 0051's refusal (R2, C2) means that a request past the adapter fails loudly instead.

**How to shard.**

- **Copy from ORT-EP: shard on a whole-unit boundary, and size the shard from the limit rounded down to the offset alignment.** ORT cuts a tensor at `maxStorageBufferBindingSize` rounded down to `minStorageBufferOffsetAlignment` (`webgpu_context.cc:237-242`) and indexes with `buffer_index = offset / CHUNK` and `local = offset % CHUNK` (`shader_variable.cc:321-340`). For a dataset, cut at a whole sample: `samplesPerShard = floor(limit / sampleBytes)`, with `sampleBytes` a multiple of 4 after packing. Then no sample crosses a shard and the gather needs no straddling read. This is simpler than ORT's element-aligned chunks, because ORT's chunks may split a vector.
- **Separate buffers or windows of one buffer.** Two designs, both correct (Proposal):
  1. One `GPUBuffer` per shard, each at most `min(maxStorageBufferBindingSize, maxBufferSize)`. This works at any source size, but each shard costs one storage binding.
  2. One buffer with several binding windows (`offset`, `size`), as ORT-EP does (`webgpu_context.cc:1263-1300`). It needs the whole source to be at most `maxBufferSize` and each offset to be a multiple of `minStorageBufferOffsetAlignment`. CIFAR-10 train satisfies both on defaults. The WIP's `bindGroupFor` key already carries `offset` and `size` (`host-entry.ts` in `fa347ad7`), so the call layer can bind windows; whether the kernel-function surface can express a window is not checked here.
     Recommendation: design 1 as the default (it never meets `maxBufferSize`), and design 2 only if upload time or memory shows a gain.
- **Budget the bindings.** A gather over S shards binds S storage buffers plus the index buffer, the output buffer and anything else the kernel reads. ORT-EP throws when the total passes `maxStorageBuffersPerShaderStage` (`shader_helper.cc:352-354`). With the default of 8, S is at most about 5. If S is above the device's budget, either (a) fall back to host batching and report the reason in `residency` (the PR's plan already says so), or (b) run one gather dispatch per shard, each writing only the batch rows whose index falls in that shard (three bindings per dispatch, S dispatches per batch, no binding cap). Option (b) is a Proposal; no reference does it. For CIFAR-10 (S = 2) the switch-over-shards form is enough and ORT's design applies.
- **Index width.** ORT's accessors use `u32` offsets (`shader_variable.cc:~321`), so one logical tensor is limited to 2^32 elements. A u8-packed dataset in `u32` words has 2^32 words, 16 GiB, so this is not a practical limit. Say so in the JSDoc.
- **Upload shard by shard.** Per shard, one `writeBuffer` or a mapped staging copy, so the host never needs a second copy of the whole source. The references upload one tensor per call and drop the host copy afterwards (`uploadToGPU` line 775, ORT `upload`). The chunk size for `writeBuffer` of a very large range (for example, 16-64 MB per call) is a guess that this report did not measure. Measure on a browser.
- **Per-epoch permutation.** One N-element u32 buffer written by `queue.writeBuffer` once per epoch. This is the cheap path in all three references (JSEP `upload`, TFJS lazy upload). If the call layer's uniform ring (3.2) holds only uniforms, the permutation stays a storage buffer.
- **Read back as little as possible.** The loss read is the one readback per step. Copy TFJS's pooled `MAP_READ` staging buffer by size (`getBufferData`, `backend_webgpu.ts:338-370`) rather than ORT-JS's new buffer on each call (`gpu-data-manager.ts:149-188`), since a training loop reads the same size each step.
- **Avoid: TFJS's CPU hand-off of small tensors** (`WEBGPU_CPU_FORWARD`, 1000 elements) in a device-resident design. It would pull a small device tensor back to the host. It only fires when all inputs are still on the CPU (`shouldExecuteOnCPU`, line 1040), so it cannot fire for a resident source. Noted so that nobody adds it.
- **Tiers.** ORT and TFJS have no tier fallback for size. TypeNN's plan (WebGPU, WebGL2, CPU, with a reported fallback) is stricter than both references. WebGL2 has its own limits (texture size), which are outside this survey.

### 3.7 Pools and uploads in the TypeShade runtime (items outside the list, found while reading)

- **Pool keys for a training loop.** Shapes repeat every step, so TFJS's exact-size key (`buffer_manager.ts:120-122`) is enough and wastes nothing. ORT's buckets pay off for variable shapes (it is built for inference with varying inputs). Copy ORT's cap on each free list (`gpu-data-manager.ts:84-113, 398-399`); TFJS has none and a changing shape sequence can grow its pool without bound.
- **Release after the submit** (all three). TypeShade's `BufferPool.take` rounds to 16 B (0051 text); keep the release at the end of the flush.
- **Do not copy `readSync` through a canvas** (`backend_webgpu.ts:379-506`).
- **Copy the debugging aid:** an error scope around each kernel when a debug flag is on, with the kernel name in the message (`backend-webgpu.ts:768-790`). It makes a validation error from a bind-group cache bug traceable, which matters for 3.2.
