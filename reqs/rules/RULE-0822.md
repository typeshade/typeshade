**Rule 8.22.** A kernel function is an exported function that is not an entry point and takes at least one array with no size (`array<T>`) or one 2D storage texture (`texture_storage_2d<F, A>`, change 0077); a sampled texture alone does not make one, so an exported helper that reads one stays a helper an entry calls; its candidate loops are the `for` and `for…of` statements at the top level of its body, and no other loop is ever a candidate.
`out.push(v)` is accepted on an array parameter of a kernel function inside a candidate loop, as a statement, with `v` of the array's element type (change 0078); a `push` anywhere else is refused, as every array method surface §63 does not list is.
A parameter of a kernel function may be ECMAScript's `Set<K>` or `Map<K, V>` (change 0080), with `K` a `u32`, an `i32`, an `f32` or a key type (Rule 4.1, change 0081) and `V` a type an array may hold; a `Map` or a `Set` anywhere else is refused (`TS8002`). `s.add(k)` and `m.set(k, v)` are statements inside a candidate loop; `c.has(k)`, `c.size` and `m.get(k)` read it, `m.get(k)` only where a `m.has(k)` of the same `m` and the same `k` guards it (the `then` of an `if`, after the `?` of a conditional, or right of an `&&`), since a shader value has no `undefined`; every other member, a local that holds one, and an `add` or a `set` outside a loop are refused (`TS8099`).
A method on the function's array (Rule 8.18, change 0079) is the loop it is written into: at the top level a candidate loop, with the function handed over as its body, so `xs.reduce((a, x) => a + x, 0.)` is R3's reduction form and `const s = xs.reduce(…)` reduces into `s`.
Its body is scalar statements, then its loops, then stores into elements of its array parameters and an optional `return` of scalars (change 0094): after its last loop, `a[k] = e`, or a compound `a[k] op= e`, stores into an element of an array parameter `a`, `k` and `e` may read its scalars, what its loops reduced, the length of an array a loop pushes onto (Rule 8.23) and the elements of its arrays, and the stores run in the order written; a store whose index is past the array's end is dropped on every tier, so the array's `.length` after it is still its length; and a function with no loop may be scalar statements and such stores (decision D7).
The statements before a loop, its start and its bound may read the scalar parameters, the elements and the `.length` of the array parameters, and what an earlier loop of the same call wrote, the length of an array an earlier loop pushes onto included, and no texture (change 0094): a loop whose range reads an element, or such a length, has a range the device holds, which the call computes in a range entry of one invocation and dispatches the loop from (Rule 11.8), and a write that such a loop makes past an array's end is dropped on every tier, so the array's `.length` after it is still its length. A loop over a range the device holds that pushes or reduces has its bound written `min(d, c)`, with `c` a value the host knows: an expression of the scalar parameters and the arrays' `.length`, read through the `const`s the bound names, as a `min` of two such values is (decision D6); its start is such a value too, and the call sizes the loop's scratch, the counts of a push and the partials of a reduction, for the iterations from that start to `c`, before anything runs. Such a loop whose bound has no such cap, one that counts down among them, a loop over a range the device holds that stores into a texture, writes an array through an `@inout` argument, or writes an array the statements before it read, and such a range in a function that takes a `Map` or a `Set`, run the whole function on the CPU in this version, and the host view says why. A statement before its last loop that writes an array, or a statement that is neither a loop, a scalar statement nor such a store, runs the whole function on the CPU, and so does a loop that reads a variable an earlier loop reduces ("split the function").
A candidate loop runs as a GPU kernel only when this proof accepts it, on the IR, with no solver and no alias analysis:

- R1: the loop is counted (Rule 7.5) with an additive constant step; a `while` and a multiplicative step are refused.
- R2: no `return` inside it, and no `break` that belongs to it (one inside a nested loop or `switch` belongs to that).
- R3: every write (an assignment, an `inout` argument, an atomic, a `textureStore`) lands on a name declared in the body; on an outer array at `a*i + c` (`a` a nonzero constant, the same at every write to that array, with each `c` in `[0, |a|)` or one `c`), at one index whose coefficient of `i` is loop-invariant, or at `i*W + x` over a nested loop of `x` from 0 to `< W`; on a texture at `vec2(i % W, i / W)`; on a reduction variable written only as `s op= e`, `s = s op e`, `s = min(s, e)` or `s = max(s, e)` with one `op` of `+ * & | ^ min max` and `e` not reading `s`; or on an integer array written only as `a[k] op= e`, a scatter reduction; or on an array parameter the loop writes only with `push` (change 0078), any number of times in an iteration and in any branch; or on a `Map` or a `Set` parameter with `set` or `add` (change 0080), any number of times in an iteration and in any branch.
- R4: an array the loop writes is read in the body only at an index it writes, a texture it stores into is loaded only at a coordinate it stores at (its `textureDimensions` is read anywhere), a reduction variable is not read, the value an atomic returns is not read, and an array the loop pushes onto is not read at all, neither an element nor its `.length`, nor is the value `push` returns, and a `Map` or a `Set` the loop adds to is not read (`has`, `get`, `size`), since each depends on the iterations before it.
- R5: a function the body calls, transitively, writes no module variable and no binding.
- R6: no barrier, no workgroup memory and no `console` call in the body or in what it calls.

A loop the proof refuses runs on the CPU, and the program is correct either way: the refusal is a warning, `TS8070`, on the loop, whose first sentence names the line and the author's own names and whose second gives the remedy, one per loop for the first reason (Rule 12.4).
On WebGPU every invocation of a workgroup that holds an iteration runs to the end of the loop's entry (change 0096): a workgroup wholly past the trip count returns as one, on a condition every invocation of it shares (its first index, from `workgroup_id` and `num_workgroups`, against the trip count), and in the workgroup that holds the last iteration a lane past the trip count runs iteration `n − 1`, its index clamped to it, with every write of the iteration (a store to an outer array, a texel store, an atomic, a store of a push, a record of a `Map` or a `Set`) masked by the lane's `live` flag; a loop that reduces gives the tree the operator's identity for such a lane, and a loop that pushes stores no count and no element for it. Where iteration `n − 1`'s lane and the clamped lane would race, the clamped lane skips the iteration under the same flag instead: a loop that reads back an element it writes, one that loads a texel it stores, one that writes through an `@inout` argument of a call, and a fused group with an edge (Rule 11.13). The results of a call do not change on any tier; the WebGL2 program and the CPU tier keep their forms.
A variable an accepted loop reduces is combined in the tree order on every tier (Rule 7.2): each iteration combines into it from the operator's identity, the iterations' values are folded 256 at a time by the workgroup tree (at stride 128, then 64, down to 1, slot `t` becomes `slot[t] op slot[t + s]`, the last block padded with the identity), the partials the same way until one is left, and the variable is combined with that last; a loop that runs no iteration leaves it as it was.
The proof also records how an accepted loop reaches each array parameter, for the planner of `typeshade/fuse` (Rule 11.13): whether every read of an array the loop does not write, and every write of an array it does, is at exactly the loop's counter `i` (the index form `a*i + c` with `a = 1` and `c = 0`, through casts and the constants the index names); whether the loop only writes the array or also reads back what it wrote; and the first access that is not at `i`.
These are facts and refuse nothing: a loop accepted without them is accepted with them.
By default, `typeshade()` and `hostFace()` write these facts into each lowered kernel function's face (change 0085). Each face carries them for each loop, with whether the loop reduces, scatters or has a `continue` of its own, and with the lowered module as portable IR; the first access that is not at `i` is worded in the author's names, with its one-based line, as `TS8070` words an access (`t[i - 1]` (line 9)). A kernel function of a module that emulates `f64` carries its WGSL under both flavors of the emulated double, `'float'` and `'integer'` (change 0073), so the owner of a call picks one at run time (Rule 11.8), and a module that emulates none carries one; the loop IR is the module before the fp64 pass, which the planner lowers under the owner's flavor (Rule 11.13).
The face also names each array parameter whose length the iteration reads (`t.length`) and the first place it does, since an array that is only measured has no element access among the facts above.
`fuse: true` retains this default. An explicit `fuse: false` omits the fusion facts and portable IR.
Facts describe the full layout; their availability does not disable ordinary-call input projection (Rule 8.23).
A kernel function may carry `@workgroup_size([n])`: one positive whole number, or one `u32` or `i32` module constant, in an array literal, read as Rule 8.7 reads `@compute`'s extent with one extent only (change 0067). It sets the workgroup of each accepted loop that does not reduce, and a function with none runs those loops at 64. A loop that reduces runs in the tree of 256 (Rule 7.2), so the attribute on a function with such a loop is refused (`TS8077`). A `@workgroup_size` on a function that is neither a kernel function nor an entry is refused (`TS8028`), and an override name is no extent in this version. The size changes the time a loop takes, not the bits it writes, since each element is written from its own index `i`.

- Rationale: a loop is how a TypeScript developer writes work over an array, and `docs/dx.md` names dispatches and workgroups as the model the developer should not have to learn first; the proof says which loops are safe to run in any order, predictably, from rules a reader can apply by hand, rather than trusting the author's assertion (Numba's `prange`).
  Only a function that takes an array with no size, or a 2D storage texture, is a kernel, so no loop that is per-invocation code today becomes a candidate: #252 measured the 48 loops of the corpus, and none is one; a sampled texture alone makes none, since an exported helper that reads one is a helper entries call (change 0077, Amendment 1).
  The proof reads an `inout` argument as a write at its call, which #252's prototype first missed six times: a method that changes an outer object carries it to the next iteration.
  The facts for the planner are written once, at build time, in the author's names, so that the run time matches them and analyzes no IR (Rule 11.13).
