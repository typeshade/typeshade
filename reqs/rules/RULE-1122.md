**Rule 11.22.** A function opts into a numerical contract by class, with `numerics(["finite-math"], function f(…) { … })` at the top of the file or with its stage call's `numerics` option, and no function is under one by default. The classes are `finite-math`, which assumes finite, non-NaN operands, and `reassociate`, which reorders `f32` arithmetic. A contract's rewrite must apply only inside the function that opted in: no pass may inline that function into another one or another one into it. It must not apply to an `f64` operand or to lowered df64 arithmetic, must not change the CPU oracle, and must enter its class with its supported domain and its measured error bound written where the rewrite is defined. A common module (Rule 11.20) must not opt in. The determinism report must list each class a function opted into as a `contract` row that names the functions under it.

- Rationale: some rewrites hold for every finite value and fail only for NaN, an infinity or the sign of a zero (`x * 0` is `0`), and some change rounding (`(a + b) + c` is `a + (b + c)`). The default optimizer refuses both, so that `-O2` computes what the oracle computes (Rule 1.3). An author who knows a function's domain may accept them for that function and no other, and the source then shows which code the oracle no longer matches bit for bit. The emulated double cancels its own error terms, so no contract reaches it (Rule 4.4), and a common module promises the oracle's bits on every tier (Rule 11.20).
