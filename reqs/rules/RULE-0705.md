**Rule 7.5.** A `for` loop means what it means in TypeScript: its initializer runs once, its condition (`true` when it has none) is tested before each trip, and its update runs after each trip and at each `continue` (change 0136). A `for` is counted when it has the counted shape: one `let` that declares an `i32` or `u32` induction variable, a constant step, and an exit that compares the induction variable to a bound; the start and the bound may be runtime values, the loop body does not write the bound, and the step moves the variable toward the bound. A runtime bound is then compared with `<`, `<=`, `>` or `>=`, and a multiplicative step with a runtime start or bound is a whole factor of 2 or more. The compiler records the counted fact of a counted `for`; any other `for` is an open loop, as a `while` is: a header with no initializer, no condition or no update, two declarations or a comma update, a counter of another type, a bound the body writes, an exit that is not one comparison with a bound, and an update that is not a constant step. A header whose start and bound are constants must reach its bound within the induction type's range, and its step must move the variable. A name the header declares with no annotation and a value written as an integer is an `i32`, or a `u32` when the value is a non-negative integer literal and the bound it is compared with is a `u32`; that is the integer type the position declares for Rule 5.1. A name it declares with any other value takes that value's type, as a `let` does. A `while` loop is an open loop and may have any `bool` condition; an open loop whose condition is constantly `true` must have a `break` or a `return` in its body. No limit is placed on a trip count. A `for…of` over an array (`array<T, N>`, or a runtime-sized storage array) is a counted loop over the array's indices, from `0` to its length; its variable is a `const` or a `let` holding a copy of the element, and the array must be a name, or a member or index path to one. A `for…in` must be refused.

- Rationale: both targets accept a runtime bound and an open loop (#203 measured each on Tint and on ANGLE), and a program over data loops over a count it learns at run time. The analyses of roadmap items 15, 18 and 21 need a counted shape, a step whose direction is known and a bound the body does not move; none of them needs the bound to be a literal (#203). Whether a `for` has that shape is a fact the compiler can tell, so the author does not say it (`OD-3`, change 0136): a `for` of another shape is the open loop a `while` is, and both targets accept each such header (measured on Tint and on ANGLE for change 0136). The cost, recorded in change 0136: a `for` no longer promises a reader that it is counted, and a mistake in a counted header (`for (let i = 0; i < n; j++)`) compiles as an open loop that may not end. `for (let i = 0; i < data.length; i++)` is the loop a TypeScript author writes first, and `data.length` is a `u32`: a counter that stayed `i32` would make it a comparison of two integer types the author never wrote. `for (const x of xs)` is the other loop a TypeScript author writes over data: its trip count is the array's length, which the body cannot change (WGSL has no array that grows), so it is a counted loop with nothing left to check. `for…in` enumerates an object's keys, which a shader value does not have. Roadmap item 15 is the first to read it: the IR `for` carries the counted fact the front end proved (`counted`, absent on an open loop: a `while`, which is a `for` over a counter it made, and a `for` that is not counted), and the proof of a kernel function's loops takes it from there (Rule 8.22). The IR `for` holds one initializer and one update, as WGSL's header does, so a header with two declarations or a comma update runs its initializer ahead of the loop and its update at the end of the body and at each `continue` of the loop, over the counter a `while` uses; each name the header declares has an IR name no other local of the function has, so nothing after the loop sees it.
