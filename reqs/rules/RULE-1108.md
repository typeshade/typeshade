**Rule 11.8.** A kernel function's call (Rule 8.21) runs on the first tier of `configure({ prefer })` that can run it, WebGPU, WebGL2 and the CPU tier being the default order: WebGPU when the function lowers (Rule 8.22) and there is a device, the CPU tier always, and WebGL2 for no kernel function yet; a list of one tier makes that tier required, and a call no tier on the list can run throws an `Error` naming each tier's reason.
Every tier computes a reduction in the tree order (Rule 7.2).
Kernel calls run one after another in the order they were made, whether or not the caller awaits them.
`resident(array)` wraps a typed array or an array of objects once in a `Resident`, which holds its own copy: a call on WebGPU uploads it the first time and binds the same buffer at every call after, reading nothing back, and `await r.read()` waits for the calls made before it and returns a new array of what it holds; a call that fails while nobody awaits it leaves its error on each `Resident` it writes, which `read()` throws. One `Resident` must not be two parameters of one call.
An entry call's tiers are fixed (Rule 8.24): WebGPU then the CPU tier for a `@compute` entry with no barrier, WebGPU alone for one with a barrier, and WebGPU, then WebGL2, then the CPU tier for a draw, where a canvas keeps the tier of its first draw; `configure` and `Resident` do not reach an entry call yet.

- Rationale: a chain of calls over the same data (a particle step, a relaxation) should pay one upload and one read, not one of each per call: #252 measured the conversion of a million 32-byte structs at about 220 ms in and 1.3 s out, which residency pays once. The order of the tiers is the caller's to set, and a caller that needs the GPU says so and gets an error that names why rather than a slow answer (#252's open question 6). The calls keep their order because a queued call has no await to order it by.
